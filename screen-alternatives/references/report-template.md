# Final Report Template & Real-World Examples

This document defines the strict output schema for the comparison report generated by the **Screen Alternatives** skill, accompanied by concrete examples.

---

## 1. Strict Output Template

The report MUST open with exactly two lines:

```text
Screen job: <one-sentence description of the screen's core purpose and user outcome>
Current screen: <factual assessment of whether it supports that job, highlighting the primary bottleneck>
```

Followed immediately by these four required sections:

```markdown
### Stress-Test Findings
| # | Element / State | What Is Wrong | What It Costs |
|---|-----------------|---------------|---------------|
| 1 | <Specific element/state> | <Concrete architectural defect> | <Measurable usability cost> |
| 2 | ... | ... | ... |

*(Maximum 8 findings, ranked strictly from strongest to weakest. No filler.)*

### Alternatives
| Alternative | Leads With | Structural Change | Findings It Answers |
|---|---|---|---|
| Alt A | <Leading visual anchor> | <Rearrangement of hierarchy/order> | #1, #3 |
| Alt B | <Leading visual anchor> | <First-principles interaction shift> | #2, #4, #5 |

### Considered but Rejected
* **<Direction 1>**: <Concrete rationale why rejected (e.g., conflicts with platform convention, requires unsupported backend capabilities, duplicates existing product pattern, or introduces skin changes)>.
* **<Direction 2>**: <Concrete rationale>.

### How to Decide
<Exactly one sentence stating the empirical test, metric, or user research method that determines the winning design.>
```

## 2. Complete Example 1: B2B Cloud Cost Alert Screen (Desktop SaaS)

```markdown
Screen job: This screen helps DevOps team leads quickly diagnose cloud cost anomalies across microservices and authorize resource throttling.
Current screen: Partially supports the job, but buries the anomalous service details beneath high-level historical line charts, delaying threat response.

### Stress-Test Findings
| # | Element / State | What Is Wrong | What It Costs |
|---|-----------------|---------------|---------------|
| 1 | Action Bar ("Throttle Cluster") | Placed at bottom-right of page after 1,200px of scrolling through historical billing graphs. | Increases time-to-mitigation during active runaway spend incidents. |
| 2 | Anomaly Alert Banner | Uses same light-blue background fill as standard informational tips. | Fails to trigger urgency; blurs distinction between warning and normal state. |
| 3 | Service Cost Breakdown Table | Displays 14 un-grouped columns with no sorting applied by default. | Forces engineers to manually scan row by row to locate the culprit service. |
| 4 | Microservice Detail State | Empty state on unselected cluster shows a blank white box with no instructions. | Confuses users on whether data failed to load or requires a row click. |
| 5 | Billing Metric Accents | Raw micro-dollar calculations ($0.00042/req) displayed at same font size as total monthly spike ($42,850). | Visual hierarchy inversion; eye drawn to irrelevant decimal precision. |

### Alternatives
| Alternative | Leads With | Structural Change | Findings It Answers |
|---|---|---|---|
| Alt A | Sticky Incident Triage Bar | Elevates cluster anomaly metric and "Throttle Cluster" CTA to a sticky top header; moves historical trend charts below the service breakdown. | #1, #2, #5 |
| Alt B | Exception-First Triage Queue | Replaces full billing dashboard with an active incident card ranking runaway clusters by spend velocity, with progressive disclosure drawer for drill-down metrics. | #1, #3, #4 |

### Considered but Rejected
* **Full-Screen Modal Dialog**: Rejected because engineers require concurrent access to live terminal telemetry and cluster logs while evaluating throttling parameters.
* **Automated Auto-Kill Toggle**: Rejected because terminating production microservices without human approval violates enterprise safety protocols and invents unsupported backend functionality.

### How to Decide
Measure median time-to-decision (MTTD) in simulated outage runs: choose Alt A if engineers rely on continuous chart context, or Alt B if single-click triage velocity yields fewer false positives.
```

## 3. Complete Example 2: Mobile E-Commerce Bag Review Screen (Mobile App)

```markdown
Screen job: This screen helps mobile shoppers review their cart items, verify delivery timing, and initiate checkout.
Current screen: Fails to support efficient checkout by burying shipping estimates and order totals beneath an aggressive cross-sell carousel.

### Stress-Test Findings
| # | Element / State | What Is Wrong | What It Costs |
|---|-----------------|---------------|---------------|
| 1 | Checkout CTA Bar | Positioned statically below a 6-item cross-sell grid, requiring 2 full screen swipes to reach. | Dramatically increases checkout abandonment at the bottom of the funnel. |
| 2 | Item Quantity Stepper | Minus icon (-) and Remove trashcan icon share identical 18x18px hitboxes spaced 6px apart. | High error rate; users accidentally delete cart items when attempting to decrement quantity. |
| 3 | Promo Code Field | Expanded open input field occupies 140px of prime viewport real estate above the item list. | Encourages coupon-hunting off-app before verifying items. |
| 4 | Estimated Delivery Date | Displayed in 11px gray text beneath product SKU numbers rather than beside the shipping option. | Users miss delivery feasibility before committing to purchase. |

### Alternatives
| Alternative | Leads With | Structural Change | Findings It Answers |
|---|---|---|---|
| Alt A | Persistent Sticky Checkout Dock | Pins order total and primary "Checkout" button to the bottom viewport edge; collapses promo code into a single-line tap disclosure. | #1, #3 |
| Alt B | Express Swipe-to-Buy Flow | Replaces vertical item stack with compact swipeable cart cards above a two-step shipping speed selector and integrated Apple Pay sheet. | #1, #2, #4 |

### Considered but Rejected
* **One-Page Checkout Fusion**: Rejected because combining bag review, shipping address entry, and credit card entry into one mobile view creates severe cognitive overload on small viewports.
* **Aggressive Urgency Timers ("Only 2 left!")**: Rejected because fake scarcity badges violate brand guidelines and introduce unverified product capabilities.

### How to Decide
A/B test on 10,000 checkout sessions measuring checkout initiation rate and cart abandonment velocity over a 7-day conversion window.
```
